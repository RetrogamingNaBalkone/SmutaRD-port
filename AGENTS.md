# Правила проекта SmutaRD-port

## Контекст и порядок работы

- Перед задачей читать [план](docs/plan.md), [handoff](docs/handoff.md)
  и соответствующий паспорт в `docs/tasks/`. Если паспорта нет, создать его
  по [шаблону](docs/tasks/TEMPLATE.md) до реализации.
- После задачи обновлять паспорт, статусы плана и handoff: выполненные работы,
  команды, фактические проверки, ограничения и следующую задачу.
  Не считать предыдущий чат доступным источником контекста.
- Целевые платформы: Windows, Linux, PortMaster, включая ARM.
  OGDoK — ориентир организации и возможностей; его код и исследования
  не заменяют проверку поведения этих двух игр.
- Использовать имеющиеся сборки Smutabor как достаточную исходную базу.
  Не ставить разработку в зависимость от поиска непатченных оригиналов.
  Происхождение образцов и известные изменения описаны в `docs/originals.md`.

## Требования к порту

- Восстанавливать игровую логику, форматы и оригинальный программный рендер
  по имеющимся образцам. Общий код двух игр выделять по подтверждённому сходству.
- Ввод и платформенную графическую обвязку реализовывать через SDL2;
  старые ограничения этих подсистем воспроизводить не требуется.
- Предусмотреть два самостоятельных рендера: оригинальный программный
  и OpenGL с совместимостью OpenGL ES 2. Программный путь должен работать
  без обязательного OpenGL-контекста; аппаратный рендер не сводить к выводу
  готового программного кадра. Не требовать desktop-only возможностей GL.
- Основное управление обеих игр: WASD с прицеливанием и обзором мышью
  (мауслук) либо геймпад с двумя стиками: левый — движение, правый —
  обзор и прицеливание. Предусмотреть переназначение действий.
  Предусмотреть сохранения и раздельные пользовательские данные двух игр.
  Совместимость с существующими сейвами исследовать до выбора формата,
  не обещать её без проверки.
- Источники игровых данных — соответствующие папки игр. Точный минимальный
  набор файлов определить исследованием `originals/`, отдельно для каждой игры.
  Для «Смуты» дополнительно запланировать опциональное чтение данных
  из первого трека CD-образа.
- Музыка «Смуты»: поддержать CD Audio из BIN+CUE и воспроизведение из папки
  треков в OGG и FLAC, по аналогии с папкой треков Smutabor.
  Чтение игровых данных из первого трека и музыкальных треков — разные задачи.
- Поддержать русский и английский текст в обеих играх. Сохранить исходные
  локализации, добавить английскую для «Смуты» и русскую для Raising Dead.
  Охват — интерфейс и игровые тексты; озвучка не входит в задачу перевода.
- Исправления игровой логики документировать отдельно от восстановления
  поведения. Не выдавать запланированное за реализованное.
- Будущие опциональные улучшения: убрать заряд алебарды и согласовать
  дальность удара с визуальным представлением; поддержать использование
  озвучки Raising Dead в «Смуте» и наоборот. Сохранить исходное поведение
  и озвучку по умолчанию; не делать эти опции условием базового порта.

## Исследования и хранение

- Декомпиляцию выполнять в Ghidra. До и после анализа проверять SHA-256
  образцов. Существенные типы, соглашения вызова и эффекты псевдокода
  проверять по дизассемблированию.
- Для выводов указывать образец, SHA-256, адресную систему, адреса
  и доказательства. Различать файловые смещения, адреса Ghidra и runtime-адреса.
  Отделять гипотезы от подтверждённых фактов.
- Автоматический экспорт не считать собираемым или проверенным исходным кодом.
  Хранить его отдельно от редактируемой реализации.
- `src/` — будущая реализация; `tools/` — воспроизводимые инструменты;
  `docs/` — решения и выводы; `analysis/` — компактные проверенные результаты.
  Не создавать пустой каркас движка без задачи.
- Постоянные локальные исследования хранить вне сборок: проекты в
  `research/ghidra/`, доказательства в `research/evidence/`, эксперименты в
  `research/experiments/`, полные экспорты в `decompiled/`.
  Эти материалы не включать в Git и поставку; правила — `docs/research.md`.
- Сборки хранить в `build/<платформа>/`, готовые пакеты — в
  `artifacts/<платформа>/`, runtime-данные при локальных проверках — в
  `user-data/<игра>/`. Не выдавать промежуточные сборки за готовый пакет.
- `originals/` не изменять и не включать в Git или поставки.
  Новые ресурсы и сторонний код сопровождать сведениями о происхождении
  и условиях использования. MIT нового кода не распространяется на игры.

## Git и проверки

- Все новые коммиты: автор и коммитер
  `RetrogamingNaBalkone <334445447+RetrogamingNaBalkone@users.noreply.github.com>`.
  Настраивать это через локальный Git config, не менять глобальную личность.
  Проверять итог через `git log -1 --format=fuller`; существующую историю
  без отдельного запроса не переписывать.
- Перед коммитом проверять diff, состав индекса и отсутствие исходных игровых
  файлов, полных экспортов и локальных артефактов.
- Выполнять проверки по характеру изменения. Для документации проверять
  ссылки и согласованность; для реализации — затронутую сборку и поведение.
  Указывать реальные команды и результаты, отдельно отмечать непроверенное.
  Не заявлять сборочные и игровые проверки до появления реализации.
