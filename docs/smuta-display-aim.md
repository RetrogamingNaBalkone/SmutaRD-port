# «Смута»: DISPDIB и автоприцел

Статическое исследование 7 ноября 2026 года в рамках [S01](tasks/S01.md).
Основа — существующая декомпиляция Ghidra; существенные аргументы, записи
и переходы сверены с её дизассемблированием. Игру не запускали.

## Образец и адреса

`originals/smuta_modern_20261013/smuta_modern/SMUTA.EXE`, SHA-256:
`1b7f8e5d010e225139f3a03f3721aff39d5e0b8c1c4ef42106c14002ea6405bb`.
Ghidra 12.1.2, PE, `x86:LE:32:default`, compiler spec `borlanddelphi`,
image base `0x00400000`; [параметры подготовки](ghidra-preparation.md).
Выводы относятся к этому изменённому образцу Smutabor.

Далее адреса — адреса Ghidra, не runtime-адреса. Для проверенных участков
CODE файловое смещение равно VA − `0x00400a00`; для DATA — VA − `0x00401800`.
Основание: CODE RVA `0x1000`, raw `0x600`; DATA RVA `0x34000`, raw `0x32800`.
Не применять эти формулы к другим секциям.

## Потребность в DISPDIB

**Для исследованного игрового EXE активная зависимость не обнаружена;
для SDL2-порта оснований требовать DISPDIB нет.**

Подтверждено:

- В таблице импортов `SMUTA.EXE`: KERNEL32, WINMM, GDI32, DDRAW, USER32
  и waveopen. DISPDIB отсутствует. Его также нет в прямых импортах
  `waveopen.dll`, `smuta_music.dll` и `SETUP.EXE`.
- Экземпляр `DISPDIB.DLL` имеет заголовок **NE**, а не PE32. SHA-256:
  `2ea7f4015beedc6d198b5e423c4ef33fab2b73b2ab8c8324a657015d8973ab79`.
  Старый формат файла не следует путать с обычной Win32 DLL.
- Создание графики `0x004044e8` вызывает `0x0040396c` и `0x004039f0`.
  Первая вызывает `DirectDrawCreate`, затем устанавливает cooperative level
  через vtable `+0x50`; вторая вызывает `SetDisplayMode` через `+0x54`
  и создаёт поверхности через `+0x18`.
- Вывод кадра `0x00403f04` идёт через `0x00403dd8` (палитра) и `0x00403cf8`.
  В последней поверхность блокируется через vtable `+0x64`, кадр
  копируется в неё функцией `0x00403ed8`, поверхность разблокируется через
  `+0x80`; при двойной буферизации вызывается `0x00403c10` (Flip).
- `StretchDIBits` в `0x00403f54` — отдельный вызов GDI32 для bitmap.
  Он не означает использование DISPDIB.
- Строка `Dispdib` есть по `0x00434f1a` (файловое `0x3371a`). Найдена
  абсолютная ссылка из таблицы данных `0x00434f00` (файловое `0x33700`),
  рядом строки `Smuta`, `Win32s`, `Readme.txt`, `Install.exe`.
  Прямых обращений инструкций к строке в экспорте не найдено.

Вероятное объяснение таблицы — остатки старой установки/совместимости.
Это гипотеза, а не восстановленная история происхождения. Утверждение
README «DLL с CD для запуска» само по себе не подтверждает использование
библиотеки исследованным EXE.

Ограничение: статические импорты не исключают динамическую загрузку.
В доступном игровом псевдокоде активного пути загрузки DISPDIB не найдено,
но контролируемый запуск рабочей копии с DLL и без неё не проводился.
Про другие исторические версии вывод не делается.

## Автоприцел

**Есть вертикальная коррекция начального направления выстрела.**
Подтверждённая цепочка игрока:

1. `0x00421cb8`, инструкции `0x00421d4a–0x00421d63`: на нужном кадре
   оружейной анимации вызывается метод игрока vtable `+0x24`, с типом цели
   **9** и кодом снаряда `номер оружия + 0x30`.
2. Конструктор игрока `0x0041ffc0` задаёт vtable `0x00436930` и записывает
   `int32 +0xb4 = 30`. В таблице по `0x00436954` находится `0x00420e98`.
   Этот метод передаёт три стековых аргумента в `0x0041fc2c`, затем
   уменьшает боезапас. Псевдокод скрывает аргументы, видимые в инструкциях
   `0x00420ea0–0x00420eae`.
3. `0x0041fc2c` создаёт снаряд и копирует 52 байта состояния позиции
   и направления стрелка в локальный блок. Высота старта учитывает
   поле стрелка `int16 +0xbe`; у игрока оно инициализировано значением −100.
4. `0x0041f8d0` ищет первый объект нужного типа вдоль текущего
   **горизонтального** направления. Шаг — −100 единиц; `0x00411480`
   продвигает координаты по таблицам углов и получает объект из сетки карты.
   Проверяются также препятствия второй сетки, их флаги и высота.
   Поиск ограничен 5000 итерациями. Перебора всех врагов по экрану нет.
5. Если текущий вертикальный луч проходит в пределах высоты цели,
   коррекция пропускается (`0x0041fd3e–0x0041fd4f`). Иначе вычисляется
   угол к середине высоты цели. Расстояние в формуле —
   `max(abs(dx), abs(dz))`, не евклидова длина.
6. Разница с текущим углом нормализуется и сворачивается ветками с константами
   360, 270, 180 и 90. Сравнение с `int32 +0xb4` строгое:
   `0x0041fe07–0x0041fe0f` меняет **локальный вертикальный угол** только
   при результате меньше порога. Для игрока порог **30°**; базовый
   конструктор `0x0041eb44` задаёт 90, но игрок переопределяет его.
   Из-за сворачивания угла нельзя безусловно заменять это абстрактным
   тестом «кратчайшая угловая разница < 30°» для произвольных углов.
7. Затем добавляется циклический разброс: вертикаль `−1, 0, +1`,
   горизонталь `−1, 0, +1, 0`. Таблицы `0x0043635c` и `0x00436368`;
   общие индексы по модулю 3 и 4 (`0x0041fe13–0x0041fe61`).
   Локальное состояние передаётся в `0x0042158c` для начальной позиции
   и направления снаряда. Положение камеры в этой цепочке не меняется.

Практический смысл: нужно навести горизонтальное направление на область
цели, а код может помочь с высотой. Поиск идёт по клеткам карты, а не по
точному пересечению силуэта на экране. Попадание не гарантировано:
остаются разброс, препятствия и дальнейшая симуляция снаряда.

Это не доказательство горизонтального захвата цели или преследования цели
снарядом в полёте. Подтверждён путь оружейной анимации игрока через общий
создатель снаряда. Соответствие номеров оружия названиям и исключения
для ближнего боя ещё не исследованы. Не утверждается, что все атаки
используют этот путь. Raising Dead в этой проверке не анализировался.
