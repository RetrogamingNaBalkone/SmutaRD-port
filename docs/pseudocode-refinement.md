# Уточнение псевдокода S01

7 ноября 2026 года. Исправлены модели десяти функций в Ghidra: четыре пары
из [оценки объединения](unified-port-assessment.md) и два вызываемых x87-helper.
Это проверенный участок исследования; весь автоматический экспорт не прошёл
такую проверку и не становится исходным кодом порта.

## Исправления и доказательства

| «Смута» / Raising Dead | Изменение | Основание и границы |
| --- | --- | --- |
| `0041181c` / `004169e0` | Явный `__cdecl`, шесть стековых аргументов: `short*`, `int`, `int`, `short`, `short*`, `int` | Чтение слотов EBP+8…+0x1c; CALL `00412827` / `004179eb` и очистка `ESP,0x18`. Семантические имена структур ещё неизвестны |
| `00412628` / `004177ec` | Явный `__cdecl`, восемь аргументов; указатели на итоговые координаты | CALL `00412b58` / `0041137b`, очистка `ESP,0x20`; чтения/записи в теле. Назначение движения остаётся рабочей интерпретацией |
| `0040e4ac` / `00424f88` | Один явный стековый указатель на непрозрачные данные; байтовая адресация полей | Вход EBP+8, поля +0x51/+0x55; отдельные тела 860 байт. Прямой CALL не найден; `__cdecl` здесь — модель стекового входа и RET без очистки, полный контракт косвенных вызывающих путей ещё не восстановлен |
| `0040840c` / `004044ec` | Шесть стековых позиций, два указателя, три signed short; первый слот оставлен `undefined4` | Чтение EBP+0xc/+0x10/+0x14/+0x18/+0x1c. Первый слот тело не читает; его смысл не установлен |
| `0042fc2c` / `00433130` | Custom storage: `float10` в ST0, signed 64-bit результат в EDX:EAX | FISTP qword и загрузка обеих половин результата. Вход больше не теряется как `in_ST0` |

Для косвенных вызовов заданы локальные call-site overrides, без назначения
непроверенных сигнатур всем методам таблицы:

- `00408449` / `00404529`: пять аргументов — объект и четыре zero-extended
  16-битных значения; caller очищает `0x14` байт.
- `00408514` / `004045f4`: шесть аргументов — объект, две signed координаты,
  указатель и два младших 16-битных значения; очистка `0x18` байт.

Результаты этих методов здесь не используются; тип результата оставлен
неопределённым. Смещения таблицы `+0x3c` / `+0x40` теперь могут печататься
как индексы `[0xf]` / `[0x10]` массива 32-битных элементов.
В новом C видны аргументы обоих вызовов и расчёты, которые прежде исчезали.

### Уточнение прежнего вывода о поле

В первоначальном C `DAT_0044f640` / `DAT_0053d640` имеют тип `int*`.
Поэтому `*(undefined2 *)(DAT + 4)` уже обозначало запись по байтовому
смещению `0x10`, как MOV в `0040842a` / `0040450a`. Это не потеря записи
и не доказательство неверного смещения. Ошибка была в интерпретации отчёта.
Теперь введена минимальная структура: указатель таблицы по +0 и поле
`field_10` по +0x10; остальное остаётся непрозрачным. Экспорт явно печатает
`->field_10`, а не неоднозначную арифметику указателей.

### Сохраняющееся ограничение x87

У helper «Смуты» инструкции `0042fc32`–`0042fc47` сохраняют control word,
устанавливают RC=11, выполняют FISTP qword и восстанавливают control word.
Соответствующее тело Raising Dead — `00433130`–`00433157`.
Для конечных значений в диапазоне int64 это **усечение к нулю**. Ghidra
продолжает печатать `ROUND(value)` и не выражает смену control word в C.
В проекте и каждом новом экспортированном файле есть явное предупреждение.
Для восстановления алгоритма читать эту операцию как x87-конверсию с RC=11;
NaN, выход за диапазон и исключения нельзя заменять переносимым C-cast
без отдельного исследования. Машинные инструкции ради красивого C не менялись.

## Воспроизведение и проверки

Из корня репозитория:

```powershell
& tools/ghidra/refine-pseudocode.ps1
& tools/ghidra/refine-pseudocode.ps1 -Verify
node tools/research/verify-refinement.cjs
```

Первый запуск копирует исходный проект в `research/ghidra/s01-refined/`,
затем применяет `tools/ghidra/RefinePseudocode.java` без auto-analysis.
Начальный проект и экспорт сохраняются. Повторный apply использует ту же
уточнённую копию; verify открывает её заново с `-readOnly`, не применяет
исправлений и сравнивает C и инструкции с сохранёнными файлами.
Драйвер берёт пути Ghidra/JDK из локального `s01-initial/run.json`.
Отсутствие маркера успешного скрипта считается ошибкой даже при exit code 0.

Фактический результат: apply и повторное открытие прошли для обеих программ;
все 14 образцов manifest совпали до/после обоих запусков. Проверены десять C
и десять листингов: байты инструкций совпали с PE; `in_stack_*` и `in_ST0`
исчезли; поле +0x10 и аргументы косвенных вызовов видны. Компактная сводка
с размерами, числом инструкций и SHA-256 экспортов:
[analysis/pseudocode-refinement.json](../analysis/pseudocode-refinement.json).

Дополнительно: PowerShell Parser для нового драйвера и
`node --check tools/research/verify-refinement.cjs` — без ошибок;
33 относительные ссылки в отчётах, S01, плане, handoff и README инструментов
проверены через `Test-Path`; `git diff --check` — без замечаний.
`git check-ignore` подтвердил исключение уточнённого проекта, журнала и C.

Локальные материалы, исключённые из Git:

- Проект: `research/ghidra/s01-refined/SmutaRD.gpr`.
- C и листинги десяти функций: `decompiled/s01-refined/<игра>/<адрес>.c|tsv`.
- Аргументы запуска и журналы apply/verify: `research/evidence/s01-refined/`.

Никаких проверок игрового поведения, сборки порта или ARM не выполнялось.
Полные структуры, назначения методов, все вызывающие пути и другие функции
не объявляются проверенными. Далее — карта цикла/загрузки DAT каждой игры
и расширение проверенных типов по мере исследования; S01 остаётся в работе.
